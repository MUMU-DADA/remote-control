# 抓帧与编码性能：实测与调优

> 测量主要使用 **720p**（720×1280 或旋转后的 1280×720）。历史数字来自
> x86_64 模拟器；本次专项优化的主机微基准、设备端到端数据分开记录。

---

## 一、结论先说

历史单路 720p 测量中，编码比抓帧更贵；多路观看和慢客户端还会引入重复编码、
传输等待与浏览器解码排队。因此应同时看抓帧、编码、传输和呈现，不能只看 fps。

本次已经实施：截图与操作锁分离，JPEG/PNG/WebP 按内容和输出参数共享编码，
PNG 减少滤波扫描，H.264 可选 libyuv 转换及独立输出轮询，传输写入期限和
前端最新帧策略。证据与限制见第十一节；下表保留为此前的单路基线。

| 环节 | 720p 实测 | 判断 |
|---|---|---|
| 抓一帧（SurfaceFlinger） | **8 ms** | 便宜。折合 ~120 fps 的上限 |
| JPEG 编码 + 投递 | **61.0 fps** | ✅ 跟得上 |
| PNG 编码 + 投递 | **45.8 fps** | ✅ 够用 |
| WebP 编码 + 投递 | **38.3 fps** | ✅ 够用 |

此前调整编码器选择前，同样是这三个格式：jpeg 61.0 / png **22.2** /
webp **20.5**。根因是走了较慢的 Skia 参数路径，详见第七节。

用户感知最直接的对比（30fps 目标，客户端实际收到多少帧）：

| @30fps 目标 | 修复前 | 修复后 |
|---|---|---|
| jpeg | 30.0 | 30.0 |
| **webp** | **20.4** ❌ | **30.0** ✅ |
| **png** | **23.1** ❌ | **30.0** ✅ |

所以：

- 历史抓帧 8ms 里包含 SF 合成和 CPU 像素拷贝。减少无用抓帧、Binder 往返、
  拷贝或另建视频 Surface 路径都需要单独测量，不能据此判定抓帧已没有余量。
- 此前的主要瓶颈在编码参数；本次继续处理重复编码、操作等待和传输积压。
  WebP 是否要进一步调低 method，仍需按目标场景测量。
- **JPEG 仍是首选格式**：帧率最高（61fps）、体积适中（43.9 KiB）。

> ⚠️ 这些是 **x86_64 模拟器 + swiftshader 软件渲染**的数字，绝对值不能直接
> 推真机。真机的 GPU、内存带宽、CPU 和硬件编码器不同，连相对关系也需复核。

## 二、怎么测的（以及几个会骗人的坑）

工具：`dev/02-native-daemon/tools/bench/stream_fps.py`

```bash
# 720p，jpeg/webp/png 各跑 8 秒对比
python3 dev/02-native-daemon/tools/bench/stream_fps.py \
    --host <设备IP> --port 8088 --fps 30 --secs 8 --compare
```

它同时报三组数，**缺一不可**：

```
投递帧率   客户端真收到多少帧        ← 用户感知
抓帧节奏   服务端 /params.capture.frames 的增长速度   ← 抓帧线程实际情况
抓帧耗时   /params.capture.lastCaptureMs              ← 底层源头成本
```

三个数对不上，就说明瓶颈在中间某一段而不是抓帧。

### 坑 1：`skipUnchanged` 会让投递帧率低到 1fps，但那不是性能问题

模拟器桌面是静态画面，默认 `skipUnchanged=1` 时只在画面变化时出帧。
第一次测的时候得到 `0.2 fps`，差点当成严重 bug —— 实际是停检在正常工作。

**测投递能力必须带 `skipUnchanged=0`**（工具默认已经带了）。

### 坑 2：按「帧间隔」算帧率是错的

一次 `read()` 可能返回好几帧，中位帧间隔会算出 0.0ms。
**必须用窗口内的帧计数**（`帧数 / 时长`），不能统计单帧间隔。

### 坑 3：宿主上同时在编译，会把模拟器测量拖慢

模拟器跑在同一台宿主机上。同一组测试：

| | jpeg@60 | webp@30 | png@30 |
|---|---|---|---|
| 宿主**正在**编译 AOSP | 47.0 fps | 17.4 fps | 20.0 fps |
| 宿主空闲 | **61.0 fps** | **20.4 fps** | **23.1 fps** |

差距大到能把结论带偏（47 vs 61）。**测性能之前先确认宿主没在编译。**

### 坑 4：别拿 NDK 版测性能

`out/ndk/` 那份是 `screencap(exec)` 后端（197ms/帧），
`out/` 那份才是 SurfaceFlinger（8ms/帧）。测之前先确认：

```bash
curl -s http://<设备IP>:8088/api/v1/config | jq -r .runtime.capture.backend
# 必须是 surfaceflinger，不能是 screencap(exec)
```

## 三、源头降采样（已实现，但 720p 场景下多半用不上）

`DisplayCaptureArgs` 的 `width`/`height` **直接决定 SF 的渲染尺寸**，不是事后缩放：

```cpp
// frameworks/native/services/surfaceflinger/SurfaceFlinger.cpp:5986
ui::Size reqSize(args.width, args.height);
...
if (args.width == 0 || args.height == 0) {
    reqSize = display->getLayerStackSpaceRect().getSize();   // ← 默认走这条
}
```

传了尺寸，SF 在**合成阶段**就只生成这么多像素 —— memfd 变小、mmap 变小、
软件降采样直接省掉。

实测（720p 源，jpeg @30fps）：

| 客户端 `maxWidth` | 抓帧耗时 | 每帧体积 |
|---|---|---|
| 720（= 原生宽度） | 8 ms | 43.9 KiB |
| 480 | **5 ms** | 24.3 KiB |

### ⚠️ 为什么 720p 场景下它多半不生效

`FrameHub` 按**所有订阅者里最大的 `maxWidth`** 抓帧，而 `defaultMaxWidth` 就是
720。所以默认配置下 `targetWidth == 原生宽度`，降采样分支根本不进。

**它只在客户端主动要更小的图时才起作用**（比如控制台在小窗口里预览）。
这不是缺陷 —— 720p 全尺寸本来就只有 0.92M 像素，SF 处理得起。

### ⚠️ 取尺寸必须用 `getDisplayState`，不能用 `getActiveDisplayMode`

```cpp
ui::DisplayState state;
SurfaceComposerClient::getDisplayState(token, &state);
const uint32_t srcW = state.layerStackSpaceRect.getWidth();
```

`getActiveDisplayMode().resolution` 是**面板物理模式**，
`layerStackSpaceRect` 才是 **SF 实际合成用的逻辑尺寸**（`wm size` 覆盖生效时
两者不一致）。用错的话高宽比会算错，画面会被拉变形。

排查过程记一笔：一开始就是用了 `getActiveDisplayMode`，在
`wm size 1440x2960` 的模拟器上才暴露出来。虽然 720p 场景走不到这条路径，
但既然是错的就修掉了。

## 四、虚拟显示镜像 —— 尚未采用，收益需验证

```cpp
static sp<IBinder> createDisplay(const String8& displayName, bool secure);
static void destroyDisplay(const sp<IBinder>& display);
```

思路：建个虚拟显示把物理显示的 layerStack 镜像过去，挂 BufferQueue，
从消费者侧 `dequeueBuffer` —— SF 合成出新帧就直接推进来，不用每次发
`captureDisplay` 请求。

**代价**：

- 有订阅时需要保持虚拟显示；应随最后一个视频订阅退出销毁，验证闲时不合成
- 需要维护 BufferQueue 的建立、格式协商和生命周期
- 若消费者仍要 CPU 图像，GraphicBuffer 的读回与拷贝依然存在；直接交给
  MediaCodec Surface 的视频路径则需要另外测量

当前仍使用按需启停的定时抓帧。历史 `misses=0` 只说明当时消费者能拿到
备好的最新帧，不能证明端到端延迟最优。虚拟显示的推帧节奏、闲时成本及吞吐
尚未实测；它仍可作为独立视频 Surface 路径的一部分评估。

## 五、MediaCodec Surface 输入 —— 独立视频路径的后续方向

scrcpy 等社区项目使用显示镜像 Surface 直接喂 MediaCodec，
避免视频编码前由 CPU 读取整帧像素。

截图接口要提供 **PNG / JPEG / WebP / 原始 RGBA**，这些仍需要 CPU 可读像素。
当前 H.264 也使用抓帧后 RGBA→NV12→MediaCodec ByteBuffer 的流程，
并未实现 Surface 输入的零拷贝路径。

后续可以让独立的视频 Surface 路径与现有截图路径并存。需要验证 Android 12
私有 API、按订阅启停、方向和分辨率变更、编码器并发能力及延迟收益；
截图需要 CPU 像素并不否定视频单独省掉这些拷贝的可能性。

## 七、根因找到了：Skia 那条"原生快路径"其实是慢路径 ✅ 已修

### 结论

`AndroidBitmap_compress`（Skia）在 WebP / PNG 上**比内置编码器慢一倍**。
直觉上"原生实现应该更快"，实测完全相反。

720p，60fps 目标，宿主空闲：

| 格式 | Skia `AndroidBitmap_compress` | 内置编码器 | 提升 | 体积变化 |
|---|---|---|---|---|
| jpeg | 60.3 fps / 43.9 KiB | 61.0 fps / 43.4 KiB | 持平 | 持平 |
| **webp** | 20.5 fps / 25.0 KiB | **38.3 fps** / 25.5 KiB | **+87%** | +2% |
| **png** | 22.2 fps / 72.9 KiB | **45.8 fps** / 85.3 KiB | **+106%** | +17% |

两组数字各自复现过，不是噪声。

### 为什么

大概率在**参数**上，而不是实现质量：

- **WebP**：Skia 用 `method=3`（为了跟 Chrome 对齐），我们内置的用 `method=2`。
  按 `webp_encoder.h` 里原有的实测，method 2 相对 3 **正好快一倍** ——
  和这里量到的 +87% 对得上。
- **PNG**：Skia 用了较高的 zlib 级别，我们默认 1（最快、最大）。

也就是说 `webp_encoder.h` 里那套参数调优**一直没生效过** ——
只要设备是 API 30+，WebP 就轮不到内置 libwebp，`kDefaultWebpMethod = 2`
是一行死代码。

### 怎么修的

`image_encoder.cpp` 里加了 `PreferBuiltin(ImageFormat)`，**按格式**选编码器：

| 格式 | 走哪条 | 理由 |
|---|---|---|
| jpeg | Skia | 持平，没必要动 |
| webp | 内置 libwebp | 快 87%，只大 2% |
| png | 内置 zlib | 快 106%，大 17%（唯一要权衡的一项） |

两个开关都留着：

```bash
REMOTE_CONTROL_FORCE_FALLBACK=1   # 全走内置（验证老设备路径）
REMOTE_CONTROL_PREFER_NATIVE=1    # 全走 Skia（要最小体积时）
```

`/params` 的 `codecs.backend` 也跟着改成**逐格式**报，不再是一个笼统的名字：

```
"backend": "jpeg=AndroidBitmap_compress + webp=libwebp（内置） + png=zlib PNG"
```

### PNG 那 17% 体积要不要认？

72.9 → 85.3 KiB/帧。按 30fps 算：2.1 MB/s → 2.5 MB/s。

- 局域网内无所谓
- 但 PNG 本来就比 JPEG 大 65% 还更慢，**它不该是控制台的默认格式**
  （默认是 jpeg）。PNG 是给"要无损"的少数场景用的，
  那种场景下 2 倍帧率比 17% 体积重要。

如果哪天要反过来，`REMOTE_CONTROL_PREFER_NATIVE=1` 就够了，不用改代码。

### 顺带确认：`webp_encoder.h` 里原有的调优是对的

| method | 320×480 | 1080p | 相对 Skia 默认(m=3) |
|---|---|---|---|
| 0 | 3.3 ms | 24.8 ms | 快 3.1x，体积 +22% |
| **2（现在的默认）** | **5.2 ms** | **38.8 ms** | **快 2.0x，体积 +3.6%** |
| 3（Skia 用的） | 10.3 ms | 78.5 ms | — |
| 6 | 21.8 ms | 126.5 ms | 慢 2.1x，体积 -5.8% |

`thread_level=0`（单线程）也是实测结论：libwebp 的线程只并行熵编码那一小段，
只快 5%，不值得为它引入线程池。

### 还剩多少余量

| 格式 | 现在 | 上限（抓帧 8ms） | 还差 |
|---|---|---|---|
| jpeg | 61.0 fps | ~120 fps | 已经被编码卡住 |
| png | 45.8 fps | ~120 fps | 编码仍是瓶颈 |
| webp | 38.3 fps | ~120 fps | 编码仍是瓶颈 |

WebP 还可通过 method=1/0 换取更短编码时间，代价是体积；是否合适应按
目标带宽、动态内容质量和多订阅者负载复测。

## 八、停检（`skipUnchanged`）原来的实现比它要省的东西还贵 ✅ 已修

### 症状

抓帧节奏 60fps、画面**完全静止**、停检开着 —— CPU 占用 **63.9%** 一个核。
一个"用来省性能"的开关，本身成了最贵的一环。

### 根因

变化检测以前是**每个客户端各自**对降采样后的缓冲区做一遍 FNV 逐字节哈希：

```cpp
uint64_t HashBytes(const uint8_t* p, size_t n) {
    uint64_t h = 1469598103934665603ULL;
    for (size_t i = 0; i < n; ++i) { h ^= p[i]; h *= 1099511628211ULL; }
    return h;
}
```

720p RGBA 是 **3.52 MB**。逐字节 + 串行乘法依赖链，实测：

| 720p（3.52 MB） | 每帧耗时 |
|---|---|
| FNV 逐字节（原实现） | **3.655 ms** |
| memcmp 全等（静态画面） | **0.081 ms**（快 **45x**） |
| memcmp 不等（一变就退出） | ~0 ms（快 66 万倍） |

60fps 下单客户端就是 **22% 一个核**，N 个客户端算 N 遍。

而且它排在 BGRA→RGBA 转换和降采样**后面** —— 也就是说，
在一帧注定要被跳过的帧上，那些像素活儿照样全做完了才发现"哦，没变"。

### 修法：把变化检测挪到抓帧层，只做一次

`FrameHub` 抓完一帧顺手跟上一帧比一次（`memcmp`），
给每帧打一个「第几代**不同**的画面」`changeGen`（内容变了才 +1）。
客户端只比一个整数：

```cpp
if (p.skipUnchanged && st->haveChangeGen &&
    f->changeGen == st->lastChangeGen) {
    *unchanged = true;
    return {};          // ← 在任何像素操作之前就返回
}
```

于是静态画面下，客户端**连 BGRA 转换和降采样都不做**，
更不用说 3.66 ms 的哈希。

### 实测（同一台设备、同一套脚本、背靠背）

| 配置 | 优化前（FNV） | 优化后（memcmp） | 变化 |
|---|---|---|---|
| 60fps **停检开** | **63.9%** CPU / 693 帧 | **40.9%** CPU / 728 帧 | **−36%** |
| 60fps **停检关** | **95.9%** CPU / 734 帧 | **76.2%** CPU / 728 帧 | **−21%** |

注意帧数是**涨的**（693→728）—— 不是靠少干活换来的 CPU 下降。

`/params` 也把省下的比例报出来了：

```
frames=2065  changeGen=3  unchanged=2062     ← 静止画面上 99.9% 的帧是白抓的
```

`unchanged / frames` 高 = 画面基本静止，停检正在起作用。

### ⚠️ 一处刻意的语义变化

现在比的是**抓帧尺寸**下的像素，不是各客户端降采样之后的。
所以客户端要的图比抓帧尺寸小时，理论上会有极少数"其实降采样后一样"的帧
被多送一次。方向是安全的（宁可多送、不可漏送），而省下的哈希是它的 45 倍。

### 还剩什么

优化后 60fps 静止画面仍占 **40.9%**，那基本上就是**抓帧本身**（8~11 ms/帧）。
也就是说：为了确认"画面没变"，我们仍然每秒钟抓 60 次。

这是「按时抓帧换取低延迟」的固有代价 —— 消费者来的时候最新帧已经备好，
不用等一次抓帧。要再往下压，只能动这个设计（比如静止一段时间后把
**探测用的**抓帧率降下来，检测到变化立刻恢复），代价是画面重新开始变化时
多等最多一个探测周期。**这是个取舍，没有做。**

## 十、还没验证的

- **真机的抓帧与编码成本**。模拟器是 swiftshader 软件渲染 + 4 vCPU，
  绝对值不能推真机。
- **源头降采样后的画质**：SF 用它的缩放滤波器（大概率双线性），
  和原来的盒式平均降采样不完全一样，锐度需要对比。
- **PNG 在动态内容的成本**：历史截图体积与编码耗时高度依赖画面内容；
  新的静态编码缓存不能替代动态内容基准。控制台默认仍为 JPEG。

## 十一、2026-10 专项优化：生成、传输与呈现

### 11.1 抓帧不再等待长手势的操作锁

`Dispatcher::Handle()` 的截图和显示查询改用 `Capture` 自身的锁，
可以与长按、滑动、文件和应用操作并行。三个抓帧后端的公开入口使用同一把锁；
单次请求的目标宽度在锁内设置并于成功或失败返回前恢复，避免不同请求互相覆盖。
触控等有状态操作仍串行化，单个抓帧后端也仍串行。

### 11.2 同内容、同参数共享图像编码

每一代不同像素拥有一个 JPEG/PNG/WebP 编码缓存，键为格式、quality、
输出宽和高。相同参数的 WebSocket/MJPEG 订阅者共享正在进行的编码和不可变结果，
缓存命中时也省去 BGRA 转换与缩放。像素未变时下一次抓帧沿用缓存；
因此 `skipUnchanged=0` 仍会按节奏传帧，但不必反复编码相同内容。

每代最多保留 8 个变体，编码失败移除条目以允许重试；等待已有编码的期限为
20ms。全部变体都在编码时，额外参数可旁路编码但不留存。H.264 因帧间参考和
编码器状态仍为每个订阅者独立编码，不进入这个缓存。

这个机制主要减少静态画面和同参数多路观看的 CPU 消耗。动态游戏中像素每帧都变，
只能复用同时消费同一代像素的相同变体，不能把静态缓存命中率推广过去。
`GET /api/v1/params` 新增累计 `encoding.encodes/cacheHits/waitTimeouts`，
测量时取窗口增量，结合 `capture.changeGen` 和 `unchanged` 判断内容是否静态。

### 11.3 PNG 减少重复扫描，输出保持相同

PNG 的 None/Sub/Up 三种滤波评分合并到一次行扫描，并直接写入压缩输入缓冲，
省去临时行结果复制和全帧预清零。保留原来的评分、平分时的选择顺序与压缩参数。

同一主机、g++ `-O2`、720×1280 合成图，旧版本与新版本各 60 轮交替测试：

| PNG | 旧版本 | 新版本两轮 | 输出大小 |
|---|---|---|---|
| level 1 | 20.1ms | 12.2 / 11.9ms | 均为 21,209 字节 |
| level 6 | 29.7ms | 21.5 / 21.2ms | 均为 6,981 字节 |

这组是主机编码微基准，不是 Android 端到端帧率。另对全零、重复横向图案、
渐变和固定 seed 随机 RGBA，五种尺寸（含 1 像素边界与 720p）、level 1/6/9
共 60 组输入比较：旧新 PNG 文件逐字节一致，独立校验 chunk CRC、deflate
长度并逆滤波后，所有 RGBA 字节与输入一致。

### 11.4 H.264 转换及输出等待

优先运行时加载系统 libyuv `ABGRToNV12`，缺库或符号时回退原标量转换；
可用 `REMOTE_CONTROL_H264_LIBYUV=0` 对照。当前单次转换测量约从 1.9ms 降至
0.3ms，仅代表 RGBA→NV12 阶段，不能当作完整视频延迟下降。MediaCodec 的输入
stride、slice height 和不足缓冲都会校验，流输出尺寸按 NV12 要求对齐到偶数。

输入等待缩短至 5ms，输出独立轮询：即使静态画面因停检停止输入，已接受的最后
一帧仍能被取出。每个 WebSocket 二进制消息只发送一个完整访问单元，
IDR 带 SPS/PPS，帧率、质量或尺寸重配置后重新发送 codec 信息。
启动、编码或输出失败会发送 `t:error` 并结束连接，避免无期限重试。
ROM 的 SELinux 策略同时补充 Codec2/OMX、mediaserver、media.metrics 和媒体配置
访问权限，避免服务查找被拒绝时的启动重试。平台、Treble 和 neverallow 构建检查
已通过；设备测量使用临时加载的 enforcing 策略与临时升级进程，未烧录新 ROM。

### 11.5 传输与浏览器积压有边界

WebSocket 使用分散发送头部和已有编码缓冲，MJPEG 同样分散发送 multipart
头、图像和尾部，减少整帧拼接复制。单次写入的 1 秒期限覆盖所有短写和等待；
失败时关闭连接，因为部分帧可能已经送出，不能在同一连接上直接跳到下一帧。
期限不是端到端延迟保证，也不会限制内核已接收数据的排队。

控制台 JPEG/PNG/WebP 同时最多一个解码任务，另保留一个最新待解码帧；
绘制在 `requestAnimationFrame` 中只取最新已解码结果并释放被替换资源。
旧连接、格式切换前的异步结果通过代数校验丢弃。H.264 超过解码队列阈值时
重置解码器并请求关键帧，避免随意丢弃参考帧造成后续花屏。

### 11.6 模拟器端到端对照

2026-10-04，Android 12 x86_64 模拟器 `emulator-5580`（含 ARM64 bridge），
1280×720、SurfaceFlinger 后端，旧版本为 `6a74a177`，新版本为本次优化工作树。
测试时临时替换运行进程并加载 enforcing 媒体策略，没有更改磁盘中的系统二进制
或烧录 ROM。旧新测试使用相同画面与流参数；受并行 policy 构建影响的中间测量
已丢弃并重测。原始 JSON、环境与复现说明见
[证据索引](evidence/stream-opt-2026-10-04/README.md)。

4 个客户端、60fps 目标、原始尺寸、`skipUnchanged=0`，静态桌面各测 5 秒：

| 指标 | PNG 旧 → 新 | JPEG 旧 → 新 |
|---|---|---|
| 各客户端投递 fps | 29.9–30.5 → 60.7–60.9 | 60.8–61.0 → 61.1–61.3 |
| 首帧 ms | 89.2–101.4 → 38.3–45.0 | 19.3–23.6 → 26.8–30.5 |
| ping p50 / p95 ms | 21.52 / 44.52 → 3.46 / 10.29 | 9.95 / 39.26 → 11.22 / 33.90 |
| 单次截图 p50 / p95 ms | 166.72 / 238.40 → 116.26 / 139.33 | 30.84 / 34.25 → 20.82 / 28.42 |

PNG 投递约翻倍，流存在时单次 PNG 截图 p50 降低约 30%。新 PNG 测量窗口抓帧
306 次，其中内容变化 1 次、未变 305 次，成功编码 1 次、共享命中 1,218 次。
这证明静态多路复用有效；JPEG 本来已接近目标帧率，这组数据没有显示帧率上的
明显增益，首帧和 ping p50 也未变快。

同样 4 路 PNG，在设置页重复滚动的 6 秒窗口：

| 指标 | 旧版本 | 新版本 |
|---|---|---|
| 各客户端投递 fps | 31.8–33.5 | 58.7–59.2 |
| ping p50 / p95 ms | 27.74 / 79.71 | 10.84 / 38.31 |
| 滚动停止后单次截图 p50 / p95 ms | 99.39 / 115.03 | 49.02 / 56.76 |

新版本抓帧 368 次、内容变化 260 次，成功编码 259 次、共享命中 1,161 次，
说明收益也覆盖了这组有变化的内容。滚动输入和动画并非逐帧确定性回放，
不能把这个倍率直接推广到游戏或高熵画面。上表的截图各取 8 个样本，均在流的
fps 测量之后、保持流连接时取得；滚动场景取截图时已停止滚动，不能称为动态
截图延迟。ping 衡量控制消息往返，fps 衡量客户端收包，均未测浏览器呈现延迟。

新版单路 H.264 静态画面、60fps 目标、原始尺寸测得 59.5fps、首帧 74.6ms。
模拟器使用软件 AVC 编码器；旧运行域曾因 SELinux 权限创建编码器失败，
因此没有可对比的旧 H.264 性能基线，不能把旧失败当成性能提升。

可用 Node 22+ 内置 WebSocket 客户端复测：

```bash
node dev/02-native-daemon/tools/bench/stream_latency.mjs \
  --base http://<设备IP>:8088 --format png --clients 4 \
  --fps 60 --width 0 --seconds 5
```

仍需补：前后同条件 CPU、更多单路/多路动态内容、浏览器呈现延迟、
拥塞链路以及真机 AVC 编码器布局。1 秒写入期限也不是端到端延迟保证。
独立 Surface 视频路径是后续评估方向，没有在本次实现中加入。
