# 依赖清单：用了什么、为什么不用手写

> 判断标准只有一条：**这段代码会不会直接处理不可信输入？**
> 会 —— 就必须是经过第三方审计的实现，手写等于自己发明密码学。
> 不会 —— 手写的小实现往往比引一个库更可控。

---

## 一、当前依赖

| 组件 | 用的什么 | 来源 | 许可 | 为什么 |
|---|---|---|---|---|
| **JSON 解析** | **jsoncpp 1.9.4** | AOSP 树内 `external/jsoncpp` | MIT | ✅ **会碰不可信输入**（HTTP 请求体、WS 消息）。见下 |
| **HTTP 客户端** | **libcurl**（运行期 dlopen） | 设备系统库 | MIT/X | ✅ 会碰不可信输入（服务端返回的数据），且是事实标准 |
| **WebP 编码** | libwebp（源码内置） | vendored | BSD-3 | 纯编码器，输入是我们自己的像素 |
| **JPEG 编码** | libjpeg（运行期 dlopen） | 设备系统库 | IJG | 同上 |
| **PNG 编码** | zlib（源码内置） | vendored | zlib | 同上 |
| **H.264 编码** | AMediaCodec | 平台 API | — | 平台硬件编码器 |
| **JSON 输出** | 自己写的 `json_writer.h` | 本项目 | — | **只输出不解析**，不碰不可信输入 |
| **HTTP 服务端** | 自己写的 `http_server.cpp` | 本项目 | — | 见第三节 |
| **令牌校验** | 自己写的恒定时间比较 | 本项目 | — | 见第四节 |

## 二、JSON：从手写换成 jsoncpp

**为什么换**：解析器是**唯一直接解析不可信输入**的组件。手写递归下降要自己处理
深度、转义、UTF-8 边界、数字溢出、代理对 —— 每一条都是历史上出过事的地方，
而我们没有任何第三方审计。

**换成了什么**：jsoncpp 1.9.4，AOSP 树内依赖（不用 vendor 源码），
AOSP 自己也在用。

**接口没动**：`json::Value` 是本项目的薄封装，调用方（`rest_api` / `clipops`）
按它写的。换引擎不必连调用方一起换 —— 那会把改动面和风险都放大，
而 `Value` 本身不解析任何东西，只是一棵已解析好的树。

**安全设置**（都在 `json_parser.cpp` 里显式写死）：

| 设置 | 值 | 为什么 |
|---|---|---|
| `stackLimit` | 32 | jsoncpp 的 reader 是递归的，默认 1000 —— 深嵌套请求体能打穿栈 |
| `strictRoot` | true | 顶层必须是对象/数组，裸标量当请求体没有意义 |
| `allowComments` | false | 放宽输入面没有好处 |
| `allowTrailingCommas` | false | 同上 |
| `rejectDups` | true | 重复键谁赢取决于实现，不如报错 |
| `failIfExtra` | true | 否则 `{} {}` 会被静默接受一半 |

> ⚠️ AOSP 编 jsoncpp 时带 `-DJSON_USE_EXCEPTION=0`，此时它的内部断言是
> `abort()` 而不是抛异常。所以只走 `parse()` 的返回值这条路，
> 不碰任何可能触发断言的操作。

**顺带拆掉的一个坑**：原来的测试断言错误信息里含「位置」二字，
换引擎后格式变成 `Line 1, Column 6`。**这种把实现细节钉死的断言，
在换实现时红一次然后被人随手改掉，从此失去意义。**
改成只断言「有没有定位信息」。

## 三、HTTP 服务端：**暂时不换**，但做了一次安全复查

AOSP 里**没有** C++ 的 HTTP 服务端库（`apache-http` / `nanohttpd` / `okhttp`
全是 Java 的）。换的话只能 vendor 一个（如 cpp-httplib，~11k 行），
并重写流式响应 / MJPEG / WebSocket 集成 —— 那些都长在现在的连接模型上。

**判断：现在换的收益小于风险。** 但复查发现了两个真问题，都已修：

### 3.1 ✅ 鉴权曾经在读完请求体之后

原先的顺序是：`ReadRequest`（读头 + 读正文）→ `CheckAuth`。
也就是说**未授权的客户端可以让服务端先收完整个请求体再被拒**。

请求体上限提到 4GB 之后，这变成一个不需要任何凭据的**磁盘打满**手段。

修法：`ReadRequest` 加一个 `onHeaders` 回调，头部解析完、正文还没读时
就判鉴权。实测：无令牌 POST 300MB →

```
HTTP 401   上传 0 字节   落盘文件 0 个   磁盘消耗 0.0 MB
```

同时**删掉了原来那份晚鉴权**。两份检查并存的结果是改了一处以为生效了、
实际被另一处先拦下 —— 这个坑本项目踩过一次。

### 3.2 ✅ 并发连接数没有上限

每个连接一个线程，而 `connFds_` 无上限。一个客户端狂开连接就能把线程和 fd
耗光。现在有 `maxConns`（默认 128），超限明确回 503 而不是默默排队或崩。

### 3.3 已有的防护（复查通过）

- 请求头上限 64KB
- 请求体上限（现在可配，默认 4GB，大体积自动落盘）
- **明确拒绝 `Transfer-Encoding: chunked`** —— 不半懂不懂地解析，
  这正是请求走私的温床
- `Content-Length` 校验符号与上限
- 每连接 `SO_RCVTIMEO`，防"连上不发数据"

## 四、令牌校验：不需要库，需要用对原语

`a == b` 对 `std::string` 是**短路**的 —— 第一个不同的字节就返回。
攻击者可以靠测量响应时间逐字节猜出令牌。局域网里没有互联网那种抖动噪声，
这种攻击完全可行。

正确做法是**恒定时间比较**：十几个字节的异或累积，走完全程不提前退出。
任何密码学库里的 `CRYPTO_memcmp` 做的也是同一件事 ——
为这点功能链一个 BoringSSL 进来，增加的是攻击面而不是安全性。

**顺带修的一个泄漏**：`?token=<令牌>` 是支持的传法之一，
而鉴权失败日志打的是 `rawPath` —— **那里面就含着令牌**。
日志会被读、被转发、被贴到工单里。现在统一走 `RedactToken()`。

## 五、怎么判断某个依赖该不该换

1. **它碰不可信输入吗？** 碰 → 必须是第三方审计过的实现。
2. **它的失败模式是什么？** 崩溃 / 越界 / 信息泄漏 → 换。
   只是算错一个值 → 手写加测试就够。
3. **换它的改动面有多大？** 接口面越小越好 ——
   本项目换 JSON 时**没动 `Value` 接口**，所以调用方一行没改。
4. **换进来的是更安全的，还是只是更多的代码？**
   vendor 一万行第三方代码，如果没解决上面第 1、2 条，那是净增攻击面。
