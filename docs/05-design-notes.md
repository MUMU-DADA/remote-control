## 一、三条传输

同一个 `Dispatcher` 处理所有请求，三种传输只是不同的"外壳"：

| 传输 | 适合 | 不适合 |
|---|---|---|
| **HTTP/JSON** | 任何语言、任何工具（curl、浏览器、脚本） | 高频事件（每次都要 TCP 往返 + HTTP 解析） |
| **WebSocket** | 实时双向：画面流、触控流、日志流 | 一次性调用 |
| **Unix socket**（SEQPACKET） | 本机、零拷贝传大块数据（截图/APK） | 跨机器 |

**能力完全一致** —— 不会出现"某个功能只有一种传输支持"，也不会出现
两边行为不一致。适配层只做格式转换（截图 → PNG、memfd → 响应体）。

### 协议约定的由来

| 方向 | 格式 | 为什么 |
|---|---|---|
| 请求 payload | **NUL 分隔的 UTF-8 字符串** | 参数少而固定。字符串本身不含 NUL，零依赖、无歧义，比 JSON 少一个解析器 |
| 应答 payload | **JSON** | 结构化、字段会增长。服务端只需要"写"不需要"读"，所以不必引解析库 |
| 大块数据 | **memfd + `SCM_RIGHTS`** | 复用截图已经在用的通道。**没有大小上限**（SEQPACKET 单条消息约 208KB 上限，APK 动辄几十 MB） |

这三条同样适用于 HTTP 层：截图 → 直接当响应体、memfd → 读出来当响应体。

### 不引入 HTTP 库

需要的只是 HTTP/1.1 的一个子集：请求行 + 头 + `Content-Length` 正文。
没有 keep-alive（一个请求一个连接），没有 chunked。

`Transfer-Encoding: chunked` 会被 **400 明确拒绝**，而不是半懂不懂地解析 ——
对安全敏感的接口，错误的解析比明确的拒绝危险得多。

### 共享抓帧：多客户端看同一块屏幕

原来每个流式客户端各自抓一次帧，而它们看的是**同一块屏幕**：

```
客户端A ──抓帧──┐
客户端B ──抓帧──┼─ 全局锁 → 3 次抓帧，2 份白做
客户端C ──抓帧──┘
```

实测总抓帧吞吐被锁住，然后被 N 个客户端瓜分。

**SurfaceFlinger 后端（正常的 AOSP 构建）**：

| | 改造前 | 改造后 |
|---|---|---|
| 1 客户端 | 每个 ~10 fps | **29.8 fps** |
| 3 客户端 | 每个掉落大半 | **30.8 fps each** |
| 总抓帧 | 随客户端翻倍 | 349 → **377**（+8%） |
| 共享命中 | 0 | **590**（3 客户端时） |

三个客户端每个都跑满 30 fps，而抓帧次数几乎没变。

> ⚠️ 第一版这组数字是在 **NDK 构建**（screencap 后端，197ms/帧）上
> 测的，得到"5.8 fps"。那个后端的抓帧本身就慢 10 倍，把共享的效果
> 完全掩盖了。**测性能之前先确认 `/api/v1/config` 里的
> `runtime.capture.backend`** —— 正确值是 `surfaceflinger`。

`FrameHub` 是一个抓帧线程 + 一份共享帧：

- **零拷贝**：`SharedFrame` 持有 memfd 的 mmap 映射，`shared_ptr`
  的删除器负责 munmap+close。一帧 1080p 是 8MB，拷一份就是浪费
- **定时抓帧，节奏 = 所有订阅者的最高需求**（见下）
- **启停**：第一个订阅者起线程，最后一个离开停线程并 join。
  **没人在看画面时一次都不抓**

#### ⚠️ 抓帧节奏：不能"按请求触发"

第一版是按请求触发（消费者调用 WaitNext 时才抓）。那样**省 CPU，
但延迟很差** —— 用户反馈"改了自适应之后变卡了"就是这个：

    消费者请求 → 这时才开始抓帧 → 等一整个抓帧周期（8~197ms）
              → 编码 → 发回

**延迟 = 抓帧耗时**，而且拿到的画面已经是一个周期之前的。

现在每个订阅者上报自己的目标帧率，抓帧线程按 `max(所有订阅者)`
持续抓，消费者来了**直接拿最新帧**：

| | 按请求触发 | 定时抓帧 |
|---|---|---|
| 取帧 | 每次等一个抓帧周期 | 最新帧已备好，**零等待** |
| 服务端 misses | 高 | **0**（实测 10/30/60 fps 下都是 0） |

时刻在抓帧**之前**排：抓帧本身要 8~197ms，放在后面会把节奏往后
推一个抓帧周期，实际帧率永远达不到目标。

#### ⚠️ 量平滑度不能看"帧间隔"

第一版用帧间隔量，得出"中位数 0.0ms、标准差 138ms"的假结论 ——
从 socket 一次 `read()` 可能带回好几帧，时间戳全挤在同一瞬间，
测的是**读取时刻**不是**到达时刻**。按时间窗口数帧才是对的。

#### 抓帧与编码是解耦的

抓帧在**自己的线程**里，编码在**每个连接各自的线程**里，两边不互相
等待。慢客户端只是少拿几帧，不会拖慢别人：

```
只有 JPEG 客户端        A=5.0fps            抓帧 41
JPEG + PNG×2（最贵）    A=5.0 B=5.0 C=5.0   抓帧 40
```

加两个最贵的编码客户端，快客户端帧率**一点没变**。

#### ⚠️ 顺带修的既有 bug：静止画面发现不了断开

流式循环靠 `write` 失败发现客户端断开 —— 但"画面没变"时根本不 write
（直接 `continue`）。于是画面一静止：

```
发现不了断开 → 循环空转 → 一直请求抓帧 → 订阅永不释放
```

实测：客户端断开 4 秒后抓帧数还在涨（27→69），订阅停在 2 不动。

**这个 bug 改共享抓帧之前就有**，只是以前每次循环都要抓一帧
（200ms），空转得慢，看不出来。新增 `PeerGone(fd)`（`poll` +
`MSG_PEEK`）在这条路径上显式检查。

WebSocket 那条本来就 `poll(POLLHUP)`，不受影响。

### ⚠️ 操作锁必须在 Dispatcher 层

原来的串行化锁在 `main.cpp` 的处理器里：

```cpp
server.Run([&](const HttpRequest& req) {
    std::lock_guard<std::mutex> lock(opMutex);   // ← 返回时就释放了
    return api->Handle(req);
});
```

但**流式响应的回调是在处理器返回之后才跑的**（`ServeConnection` 拿到
响应后才调 `streamer`）。也就是说 WebSocket 里流的每个触控点都是
**无锁注入**的 —— 和并发的 HTTP 请求会互相破坏手势状态。

锁移进 `Dispatcher::Handle` 之后，无论谁调、从哪条传输调都自动串行。

代价：一次抓帧（8–12ms）会让同时在跑的触控事件排队十几毫秒。
这个开销是必要的 —— `Injector` 是有状态的（按下/抬起、槽位映射、
手势 downTime）。

### ⚠️ 关闭时的资源清理

连接线程是 detached 的，主线程走到 `main()` 结尾就析构了 `Dispatcher`
（含它的操作锁），而流式回调还在那些线程里跑：

```
FORTIFY: pthread_mutex_lock called on a destroyed mutex
```

`HttpServer::Stop()` 因此会主动 shutdown 活跃连接并等它们退出（最多 2 秒）。

## 二、截图与画面流

### 后端：SurfaceFlinger 直连 vs `screencap` exec

| | screencap（exec） | SurfaceFlinger 直连 |
|---|---|---|
| 单次抓帧 | **197 ms** | **8–12 ms**（720p，快 20 倍） |
| 流帧率 | 9.6 fps | 61 fps（jpeg，720p） |
| 依赖 | 无（任何 root 设备） | 平台私有库（要 AOSP 构建） |

> 表格里是**当前口径**（720p）。早期在 320×480 / 1440×2960 上量到过
> 120 ms vs 23 ms —— 分辨率不同，别混着比。测量条件和复现命令见
> [`06-capture-performance.md`](06-capture-performance.md)。

两条都留着：NDK 构建走 screencap（**任何 root 设备都能跑**），
AOSP 构建走 SF 直连（快）。

### 性能：9.6 → 29.8 fps 的经过（第一轮）

**先测量再优化。** 当时的瓶颈在抓帧，不在编码：

```
screencap exec 120ms/次  →  单这一项就封顶 8.3 fps
```

换 SF 后端是主要手段。另外三项优化（对两种后端都有效）：

| 参数 | 默认 | 作用 |
|---|---|---|
| `maxWidth` | 720 | 降采样。**盒式平均而不是最近邻** —— 最近邻会把细线（文字、边框）整条丢掉，看起来像画面在闪 |
| `skipUnchanged` | 1 | 画面没变就整帧跳过编码。静止画面下编码开销归零（实测 10 秒只发 1 帧） |
| `quality` | 按格式 | PNG 1-9（zlib 级别）/ JPEG·WebP 1-100 |

> ⚠️ **「瓶颈完全在抓帧」这个结论后来被推翻了 —— 它只在 screencap 后端上成立。**
>
> 换成 SF 后端之后抓帧降到 8–12 ms，瓶颈就转移到了**编码**：
> WebP/PNG 在 720p 上跑不到 30fps，而 JPEG 能跑 61fps。后来发现是
> `AndroidBitmap_compress`（Skia）的参数比内置编码器差一倍，改成
> 按格式选之后 WebP +87%、PNG +106%。
>
> **完整实测见 [`06-capture-performance.md`](06-capture-performance.md)** ——
> 那里还有测量纪律（宿主编译会污染模拟器的测量结果）。
>
> 教训：**性能结论要连着它的前提一起记**。"瓶颈在抓帧"在 screencap 上对、
> 在 SF 上错，而两句话看起来一模一样。

### 编解码器：PNG 是错的

一帧 320×480 的 PNG 要 **86 KB**。PNG 无损、为"存一张图"设计，
不是为"传一路流"设计 —— 压缩级别从 1 提到 6 **只省 22%**，
却把帧率从 30 拖到 27.5：花大代价换小收益，方向本身就错了。

改用 JPEG/WebP（`AndroidBitmap_compress`，Skia 内部实现）：

| 格式 | 帧大小 | 带宽 @30fps |
|---|---|---|
| PNG q1 | 86 KB | 2233 KB/s |
| **JPEG q75** | **14 KB** | **418 KB/s** |
| WebP q75 | 更小 | — |

**为什么不用设备上的 libjpeg**：设备上确实有 `/system/lib64/libjpeg.so`
（含 `jpeg_mem_dest`），但调它要 `jpeglib.h` 里的 `jpeg_compress_struct`
布局 —— 那个结构体很大且随版本变，NDK 里没有头文件，自己声明等于赌 ABI。
`AndroidBitmap_compress` 是 NDK 正式 API，用**写回调**直接收进
`std::string`（连 memfd 都省了），还顺带支持 WebP。

> ⚠️ 但**现在 WebP/PNG 不走 Skia 了** —— 实测它在这两种格式上比
> 内置编码器慢一倍（见 `03-reference.md` 的「编码器现在按格式选」）。
> Skia 只留着跑 JPEG，那里两者持平。

### ⚠️ 卡顿的真正原因：网页把帧率锁死在 5fps

**这一节单独写，因为第一次的"优化"根本没解决用户看到的问题。**

服务端实测 30 fps、帧间隔中位 33.5ms、236 帧 0 卡顿 —— 数据很干净。
但用户说"卡到爆炸"。**两个测量测的是不同东西。**

原因在网页控制台里：

```js
let fps = 5;                                    // ← 默认只有 5 fps
<button onclick="setFps(10)">10fps</button>     // ← 上限只有 10
```

我一直在用 `curl` 直接打 API，而网页根本没用上服务端的能力。

> **教训：测量要测用户实际走的那条路，不是测最理想的那条。**

### `auto` 的含义随场景变

| 场景 | `auto` 解析为 | 为什么 |
|---|---|---|
| 单次截图 `/capture` | PNG | 一次调用，大小不重要，清晰更重要 |
| 画面流 `/stream` | JPEG | 一路视频，带宽和编码耗时都重要 |

两个默认值不同是**有意**的，不是不一致。

### ⚠️ `?format=` 曾经被静默忽略

早先 `/capture` 只认 `raw`，其余一律 PNG：

```
?format=jpeg   → 静默返回 PNG
?format=bogus  → 也静默返回 PNG
```

调用方拿到 PNG 却以为要到了 JPEG，而且没有任何提示。
现在和 `/stream` 共用同一套解析，未知格式明确 400。

## 三、输入注入

### 为什么走 `/dev/uinput`

Android 12 **没有可用的 native 注入接口**：`IInputManager` 是 Java-only，
`IInputFlinger` 没有注入方法。uinput 是唯一路径，触控和按键都走它。

键盘是**独立的第二个设备**，不跟触控共用一个 fd —— 混在一起的话
InputReader 会把它当成"既能触摸又能打字的怪东西"，
`.idc` 里 `touch.deviceType` 与 keyboard 的判定会互相干扰。

### 手势的时序有硬要求

这三个不是 `Tap`/`Swipe` 的语法糖：

| 手势 | 时序要求 | 不这么做会怎样 |
|---|---|---|
| 长按 | 按下后**一个 MOVE 都不能发** | 系统判成拖拽，长按菜单不弹 |
| 拖拽 | 起点先停顿 120ms，再慢速移动 | 被判成滑动（fling） |
| 双击 | 两次点击间隔 120ms | 太慢超过系统阈值就不算双击 |

让调用方自己拼 `Touch*` 序列几乎一定会踩这些，所以内置。

### 键名解析的两个坑

**单字符先按字符解释，再考虑当数字键码。**
`"1"` 既可能是"数字键 1"（`KEY_1` = 2），也可能是"键码 1"（`KEY_ESC`）。
先走数字解析的话 `key "1"` 会变成 ESC —— 实测就是这么错的。

**F 键不能用 `KEY_F1 + (n-1)`。**
F1..F10 是 59..68，然后 **F11/F12 跳到 87/88**（中间是别的功能键）。
按公式算 `f12` 会得到 70 —— 一个不存在的位置。

### 流式触控

一个手势一个 HTTP 请求行不通，两层原因：

1. **延迟** —— 每次 POST 要 TCP 往返 + HTTP 解析 + 分发，
   拖拽时每个移动点都这么来一遍
2. **方向** —— HTTP 是"客户端发起、服务端应答"，而拖拽需要一条
   持续的事件流；用 POST 的话服务端只能等整个手势发完才知道轨迹

实测：

| | WebSocket | HTTP POST |
|---|---|---|
| 单事件往返（中位） | **1.1 ms** | 13.8 ms |
| 60 点拖拽 | **48 ms** | 865 ms |
| 中途反馈 | **有，每点实时** | 无（整条路径盲发） |

**`move` 默认不回复** —— 它最频繁，回一个等于把上行流量翻倍，
而客户端不需要。出错时仍然回。

**长按不需要专门命令**：流式模型里"按下 → 手指不动 → 延迟抬起"
本来就是长按。这正是流式的自然之处。

### 网页端的两个实现细节

**移动用 `requestAnimationFrame` 合并**：`pointermove` 在高刷屏上能到
200Hz，而设备侧的注入和屏幕刷新都跟不上；全发只是白占带宽。

**只在贴近底部时自动滚动日志**：用户往上翻看历史时把他拽回底部，
是最招人烦的行为之一。

## 四、应用与文件

### ⚠️ 上传 APK 曾经「传不上去」—— 64 MB 的隐形天花板

症状是网页控制端点「上传安装 APK」后报错，小 APK 却正常。

根因在 HTTP 层：**请求体全量读进 `std::string`**，所以上限只能定 64 MB。
稍大的 APK（带 native 库的、游戏的，动辄几百 MB）直接被
`413 请求体超过上限 67108864 字节` 挡掉 —— 而且服务端是按
`Content-Length` 在读正文**之前**就拒的，客户端看到的是"秒失败"。

改法：**超过 4 MB 的请求体落盘**，不留在内存里。

| | 之前 | 现在 |
|---|---|---|
| 请求体 | 全量进内存 | >4 MB 落盘到临时文件 |
| 上限 | 64 MB | **4 GB**（受磁盘约束，不受内存约束） |
| 80 MB APK | `413` 拒绝 | 正常上传安装 |
| 上传时 RSS | +APK 大小 | 不变（实测 49 MB 持平） |

顺带修的两件事：

- **不用把 APK 抄三遍**。原先 HTTP 层写 `/sdcard` → Dispatcher 再拷到
  `/data/local/tmp` → `pm install`。现在落盘的那份直接用，少一次全量拷贝。
- **控制台把「上传被拒」和「安装失败」分开报**。以前 413 也报成
  "安装失败：请求体超过上限"，用户会去查应用签名，方向完全错了。
  同时换成 XHR 加上传进度 —— 几百 MB 传几分钟，`fetch` 给不了进度，
  用户分不清是在传还是卡死了。

> 教训：**一个写死的"够用了"的上限，迟早会撞上真实文件。**
> 64 MB 对 APK 来说太小了，而报错信息（"安装失败"）还把人往错方向引。

### ⚠️ 按键：名字对不代表功能对（Generic.kl 会把扫描码翻成别的）

用户报「传 d 出来 f」，修完字母之后又报「home 失效」。

字母那半是 `KEY_A + (c - 'a')` —— 字母键码按 QWERTY 物理位置编号，
只有 'a' 碰巧对。**见下面「按键字母映射」那段。**

home 那半更隐蔽：**Linux 常量名和 Android 的行为对不上**。
设备上的 `Generic.kl` 才是权威：

```
key 102  MOVE_HOME     ← Linux 的 KEY_HOME(102) 是"光标移到行首"
key 172  HOME          ← Linux 的 KEY_HOMEPAGE(172) 才是"回桌面"
key 150  EXPLORER      ← 不是 172（那会把人送回桌面）
key 353  DPAD_CENTER   ← 不是 352（KEY_OK 在 Generic.kl 里没有映射）
```

也就是说表里写 `{"home", KEY_HOME}` 时，**扫描码"没错"、名字"没错"，
但功能是错的**。send 一个 102 出去，Android 那边得到 `KEYCODE_MOVE_HOME`，
桌面纹丝不动。

更糟的是表里那条注释写的是 `// 172` —— 常量是 102、注释是 172，
**注释断言了一个假事实，比没有注释更坏**：它让人以为已经核对过了。

> 教训：**这个项目的键名表要按"Android 那边的行为"组织，不是按
> "Linux 头文件里的名字"。** 测试也照这个来 —— 现在断言的是每个键
> 经 Generic.kl 翻译后的 Android keycode（`test_keyboard.cpp` 的 [3] 段），
> 光断言扫描码会一路绿着放它过去。

### ⚠️ 转屏后触控位置错误：坐标空间和显示尺寸脱节

用户报「转成横屏后，触控相关 api 实际触控位置错误」。

根因有两层：

**第一层：坐标空间是启动时定死的，不跟显示走。**
uinput 的 ABS 范围在设备创建时就固定了，客户端按它发坐标。
转屏后显示变成 1280x720 而范围还是 720x1280 ——
客户端按屏幕像素发 `x=1000`，超出 0..719 会被内核**钳到右边缘**，
落点全错。

> ⚠️ 这个 bug **只测屏幕正中央是发现不了的** —— 两个坐标空间在中心点
> 恰好重合。上一轮我就是只测了中心，结论写成"坐标空间是稳定的归一化空间，
> 转屏不影响"。**测一个恰好落在两种假设重合点上的值，等于没测。**

**第二层：两个旋转机制会互相打架。**
`Rotate` 有两条路：正规的 `cmd window user-rotation lock N`，
和设备转不动时的退路 `wm size WxH`。实测这台 ROM 上前者会把
`mRotation` 设成 1 但**不改变逻辑尺寸**，而后者改逻辑尺寸。
**两个同时生效时，实测逻辑尺寸被按回 720x1280** ——
抓帧还是竖屏，但接口报的是横屏尺寸。

修法：
- `Rotate` 走 `wm size` 退路之前**先把旋转锁归零**，让一个机制独占
- 几何真的变了之后**重建注入器**，让坐标范围跟着显示走
  （用户用 `--touch-range` 显式指定过就不动）

改完之后 `/info` 的 `primaryWidth/Height` 和 `touchWidth/Height` **默认一致**
（`--touch-range` 显式指定过的除外 —— 那时不动注入器，两者就是会分叉）。
所以**别缓存 `/info`**：`POST /rotate` 之后要重新读一次。
坐标空间的完整说明见 [`docs/api/01-http.md`](api/01-http.md) 的「坐标」。

### 文件管理的边界：从下载目录抬到共享存储根

一开始 `FileOps` 被沙箱在 `/sdcard/Download` 里，理由是"下载目录够用"。
但设备管理本来就该能管整个共享存储 —— 用户要的是
**「app 能读到的那个根目录」**，也就是 `/storage/emulated/0`。

改动：
- `ResolveInside` 的边界从下载目录抬到存储根
- 相对路径**仍然**相对下载目录（老客户端不用改）
- `/sdcard`、`/data/media/0` 这类**别名**自动换算 —— 只在 `realpath`
  确认它们确实指向同一个存储时才认，不盲信名字
- `FileEntry.path` 从"相对下载目录"改成**绝对路径**：加了存储根之后
  "相对谁"不再唯一
- 新增 `op=roots` 让客户端**问出**边界，而不是猜或翻文档

⚠️ 这是整个共享存储的读写权限，不只是下载目录。服务本身已经能点屏幕、
装应用、重启设备，所以不是新的信任边界 —— 但默认不鉴权 + 绑 `0.0.0.0`
的组合下，同网络任何人都能删文件。文档里明确写了这一点。

边界逻辑现在有单元测试（`tests/test_fileops.cpp`，18 项），
因为这个函数是唯一的越界防线，而且在"放宽边界"这种改动里最容易出错。

### 应用与文件的其他取舍


### ⚠️ 安全边界：路径约束

**所有路径参数都来自客户端，而 remote-control 以 root 运行。
一个 `../..` 就能删掉 `/data`。**

所以每个入口都强制走 `FileOps::ResolveInside()`，把路径约束在下载目录内：

```cpp
// 逐段规范化，遇到 ".." 且栈已空 = 试图逃逸 → 拒绝
// 绝对路径只接受已经在下载目录里的
// 再对**已存在的最深祖先**做 realpath，确认软链接没有指到外面
```

**软链接检查不能省**：下载目录里一个指向 `/data` 的软链接，
会让 `../` 检查形同虚设 —— 因为文件系统层面它确实"在"下载目录下。

实测（全部被拒，错误信息可读）：

```
../../data/system/users.xml   → 路径越界（..）
/data/system/packages.xml     → 路径不在下载目录内
../DCIM                       → 路径越界（..）
```

### 上游依赖与缺失时的行为

| 命令 | 依赖 | 缺失时 |
|---|---|---|
| 应用管理全部 | `/system/bin/{pm,am,cmd,dumpsys}` | `kErrUnsupported` + 列出缺哪个 |
| Download | `libcurl.so`（**运行时 dlopen**） | `kErrUnsupported` + 提示改用客户端推送 |
| FileOp | 下载目录存在 | `kErrUnsupported` + 列出试过的路径 |
| KeyEvent | `/dev/uinput` 可写 | `kErrUnsupported` + 原因 |
| Clipboard | `cliptool.jar` | `kErrUnsupported` + 提示怎么装 |

**都是明确的错误消息，不是静默失败** —— 而且 `/describe` 会把这些
后果提前告诉调用方。

### Download 为什么 dlopen libcurl

- NDK 里**没有** curl 的头文件和库，直接链接的话 NDK 构建就没有下载能力
- 而设备上 `/system/lib64/libcurl.so` 是有的（VNDK），实测可加载
- 所以运行期探测、有就用，两种构建共用一条代码路径

安全限制（都是刻意的）：只允许 `http`/`https`，**重定向后也只允许这两个**
（否则一个 302 到 `file://` 就能把本地文件读出来）；有大小上限，
超了立刻中止并删掉半截文件。

### 安装：为什么是临时文件而不是 memfd

`pm install` 只接受**路径**，不读 stdin。所以服务端把内容落到临时文件
再 `pm install`，**不管成败都删**。

HTTP 那层也一样：上传的 APK 落成真实文件，成功、失败、连打开失败都删。
不删的话每次安装都在 `/sdcard` 上留一个几十 MB 的 APK，
用一阵子就是一堆，而且没人会想起来清。

### 剪贴板：为什么是个 Java 辅助工具

1. **NDK 构建里没有 libbinder** —— daemon 发不了 Binder 事务
2. **访问控制按「UID + 包名」判定**：

   | 身份 | 结果 |
   |---|---|
   | root + 包名 `android` | ❌ 被拒（"not in focus"） |
   | shell(2000) + `com.android.shell` | ✅ 通过 |

   因为 `com.android.shell` 持有 `READ_CLIPBOARD_IN_BACKGROUND`。
   **daemon 是 root，所以要先 `setuid(2000)` 再 exec。**

3. **不能靠 `service call`** —— 返回的是编组过的 `ClipData` Parcel，
   从十六进制里解析它既啰嗦又随版本变。

⚠️ **写入必须回读确认**：`ClipboardService` 在权限不足时是
**静默 `return` 不抛异常**的 —— "没报错"不等于"写进去了"。

### ⚠️ 运行中应用的系统判定要三条一起看

| 判据 | 盲区 |
|---|---|
| 包名在 `pm list packages -s` 里 | 覆盖不到没有对应包的进程（`system_server` 的进程名就叫 `system`） |
| uid 不是 `u0aNN` 形式 | launcher3 这类预装应用用的是 app uid（`u0a90`），会漏 |
| 进程名含 `.process.` | 取前面那段当包名再查（`android.process.acore` → `android`） |

数据源是 `dumpsys activity lru` 而不是 `ps`：ps 给的是 UID 不是包名，
而且要额外查 PackageManager 才能对上。

## 五、服务自身

### ⚠️ 按键注入：字母键码不是连续的

用户报「传 d 实际出来 f」。

根因是 `ResolveKeyCode` 里写的 `KEY_A + (c - 'a')`。
**字母键码按 QWERTY 物理位置编号，不是字母表顺序**：

```
A=30  B=48  C=46  D=32  E=18  F=33  G=34  H=35
I=23  J=36  K=37  L=38  M=50  N=49  O=24  P=25
Q=16  R=19  S=31  T=20  U=22  V=47  W=17  X=45
Y=21  Z=44
```

所以 `+ (c-'a')` 只有 `'a'` 碰巧对：`'d'` 算出 33，而 33 是 `KEY_F`
—— 正是用户看到的。**除了 a，25 个字母全错。**

**为什么测试没抓到**：原用例只写了两条 —— `{"a", 30}` 和 `{"z", 55}`。
而 **55 是错的**（`KEY_Z` 是 44）。55 正是那个错误公式算出来的值，
也就是说**测试把 bug 固化了下来**：它验证的是「实现和自己一致」，
不是「实现和内核一致」。

现在 26 个字母逐个核对，期望值一律取自内核头文件
（`bionic/libc/kernel/uapi/linux/input-event-codes.h`），并加了一条
「字母键码**不连续**」的断言 —— 谁再想"优化"成加法，这里立刻红。

> 教训：**从实现反推期望值的测试，等于没测。**
> 只看它红了没有，看不出它钉的是不是事实。



### 配置文件放 `/sdcard`

上位应用是普通 Android 应用（**没有 root**），守护进程是 root。
两边都能读写、都不需要特殊权限的位置，就是共享存储。
放 `/data/local/tmp` 的话应用够不着。

纯文本 `key=value` 而不是 JSON：应用侧要用 Java 读写它，
引 JSON 库只为存五个字段不划算，而且双方各用一套实现时格式分歧
会变成很难查的兼容性问题。

优先级：**命令行显式给的 > 配置文件 > 内置默认**。
上位应用不传命令行参数，所以它能生效；调试时 `--http-port 9999`
这种一次性覆盖也不会被文件悄悄改掉。

### ⚠️ 服务开关是软开关

关闭服务**不真停进程**，只是不再对外提供能力。

**为什么**：真停了就没人能开回来 —— 网页打不开、接口不通，
只能跑到机器跟前救。所以关掉之后仍然留两个入口：

| 入口 | 为什么留着 |
|---|---|
| `GET /`（网页本身） | 不放行的话浏览器里只有一个 503 的 JSON，用户够不着开关 |
| `POST /api/v1/service` | API 客户端重新开启的入口 |

**socket 路径也要挡** —— 不然"关掉服务"只是关掉了 HTTP，
本机进程照样能通过 socket 完整控制设备，软开关就成了摆设。

### ⚠️ 配置文件要实时生效

守护进程启动时读一次配置，但上位应用改的是**文件**。
所以有一个监视线程（每 2s 查 mtime）专门处理 `enabled`。

实测踩过：配置文件里 `enabled=1`，运行中的服务还是关着的 ——
因为只在启动时读过。

**只处理 `enabled`**。`bind`/`port`/`auth` 改了必须重启进程，
由 supervisor 负责 —— 热改会让正在看的画面流和触控连接莫名其妙断掉。

### 日志

| | 说明 |
|---|---|
| 内存环形缓冲 | 2048 行，按 `sinceSeq` 增量拉 |
| 落盘历史 | `/sdcard/remote-control.log`，**最多 10KB** |
| 日志流 | WebSocket，按序号增量推 |

裁剪带**滞回**：超过 10KB 裁到 7.5KB。裁到"刚好 10KB"的话下一行又超、
又裁一次 —— 每写一行就要读写 20KB。

时间前缀在**缓冲层统一打**，而不是让每个写入点自己格式化 ——
写入点遍布各处，漏一个就会出现没有时间的日志行。

内存里同时保留单调时钟和墙上时间：排序和增量拉取用单调时钟更稳
（不受系统时间被改的影响），"几点发生的"只有墙上时间能给。

### supervisor：让无 root 的应用能管 root 服务

```
上位应用 → 写 /sdcard/remote-control.conf
remote-control-supervisord（常驻 root 脚本）→ 监视文件 → 启停/重启
                                  → 写 /sdcard/remote-control.status 供应用显示
```

应用侧只依赖"文件能写"这一件事，**不需要任何特权**。

状态走**文件**而不是探端口：端口可能被转发规则挡住，
"进程在不在"才是确定的；而且服务没起来时探端口只会得到"连不上"，
分不清是挂了还是没启动。

### 上位应用为什么只剩三件事

原来的画面、触控、应用管理、文件管理**全删了**（1390 行 → 450 行）。

理由：那些能力已经是网页控制台的一部分，而网页不用装在设备上。
应用真正的独有价值是**它是设备本地的** —— 服务没起来、端口改错
导致连不上时，网页自己也进不去，只有本机应用还能把服务拉回来。

## 六、局域网访问

`adb forward` 和模拟器都**只监听 127.0.0.1**。两种暴露方式：

### 端口转发（当前用法）

```
0.0.0.0:15555  → 127.0.0.1:5555    (模拟器自身)   → adb
```

暴露之后：

| 地址 | 用途 |
|---|---|
| `http://<本机IP>:8088/` | 网页控制台（实时画面 + 触控 + 按键） |
| `http://<本机IP>:8088/api/v1/...` | HTTP API |
| `adb connect <本机IP>:15555` | 完整 adb（可用 scrcpy） |

HTTP 不再需要转发：remote-control 自己读配置里的 `bind`，可以直接绑 `0.0.0.0`。
多一层转发反而让"改端口"变成一个改完就失联的操作 ——
上位应用改了 remote-control 的端口，转发器还指着旧端口，两边对不上。

### 为什么不用真桥接（`-net-tap` + 网桥）

模拟器确实支持 `-net-tap <interface>`，真桥接能让 guest 直接从物理
路由器拿到局域网 IP。但**在远程机器上这么做风险太高**：

把 `ens33` 加进网桥并迁移 IP 的过程中必然有一个"没有 IP"的窗口 ——
SSH 会当场断开，配错了只能到机器跟前救。

端口转发能达到同样的访问效果，且不动网络配置、随时可停。

| 剪贴板 set 报成功但没写进去 | `ClipboardService` 权限不足时**静默 return**，必须回读确认 |
| 服务关了但本机还能控制设备 | socket 路径没做服务开关检查 |
| 配置文件改了不生效 | 守护进程只在启动时读一次 |
| AOSP 构建报 `cannot use 'try' with exceptions disabled` | AOSP 默认 `-fno-exceptions` |

### 编码并发限制（EncodePool）

共享抓帧解决了"N 个客户端 = N 次抓帧"，剩下的是**N 个客户端 = N 个并发编码**：

```
共享帧发布 → 所有客户端同时被唤醒 → 同时开始编码
```

单个编码不贵（JPEG 1.1ms，占帧预算 3%），但它们是**同时**发生的。
6 个客户端在 4 核上就是 6 路并发抢 CPU —— 连抓帧都被拖慢。

#### 实测：值不值得

| 编码器 | 6 客户端，不限 | 6 客户端，限制到 4 |
|---|---|---|
| JPEG（1.1ms） | 9.1 fps | 8.5 fps（噪声级，略差） |
| **PNG（13ms）** | 6.6 fps / 抓帧 54 | **8.1 fps / 抓帧 66（+23%）** |

> ⚠️ 同上：这组也是在 NDK/screencap 后端上测的（绝对值偏低）。
> 相对关系（贵的编码器下限制有用）成立，绝对数字不代表 SF 后端。

**贵的编码器下限制明显有用**：不限时 6 路 PNG 抢满 CPU，抓帧次数
从 66 掉到 54 —— 编码把抓帧饿死了。限制之后整体反而更快。

便宜的编码器下基本是中性的（8.5 vs 9.1 在噪声范围内）。

#### 为什么是"计数信号量"而不是"工作队列"

一个真正的工作池（提交任务 → 空闲 worker 编码 → 回调送出去）在这里
没有好处：结果要发回**特定的那条连接**、每个客户端的编码参数不同
（不可互换）、编码本身纯 CPU（换哪个线程做都一样）。需要的只是
"同时最多 K 个在编"。

超时（拿不到名额）**不是错误** —— 调用方跳过这一帧继续下一轮。
堵在那里的话连客户端的 fps/画质控制消息都收不到（它们在同一个循环里）。

⚠️ 用 RAII 守卫，别手写 Acquire/Release —— 编码路径有好几个提前
return 的分支，漏一个名额就永久丢了，丢够 K 个之后整个服务再也
编不出任何东西。

`GET /api/v1/stats` 的 `encodePool` 段能看到 `limit` / `inUse` /
`acquired` / `timeouts`。
